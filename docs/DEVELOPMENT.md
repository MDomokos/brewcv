# Developing BrewCV

Everything behind the app: how it's built, how it's checked, how it ships, and how private data is kept out of the repo. For what the app does and how to use it, see the [README](../README.md).

## Principles

Vanilla HTML, CSS and JavaScript: no build step, no bundler, no framework, no runtime dependency. What is in this repo is what the browser runs, and it has to still run in 2029 without `npm install` resolving.

Every file it writes is a valid [JSON Resume](https://jsonresume.org/schema). The record's summary and highlights are each claim's default version; versions, languages and tags live under `meta.resumeBuilder`. A saved resume is its own file: the resume as printed (any JSON Resume community theme can render it), with its selection under `meta.resumeBuilder.resume`.

A **format** owns the page and a **theme** owns the appearance. Neither references the other, which is what lets one theme render at both sizes.

## Translations

Every catalogue but English is **machine-written and needs a native review**; the app says so where you choose one. Corrections go in `src/i18n/<lang>.js`, and `checks/i18n-check.mjs` keeps them honest (keys, placeholders, plurals, markup, the review marker).

## Running the checks

```
node checks/run.mjs                   every Node check (about 40, side by side, a few seconds) and one summary:
                                      a line each with PASS or FAIL and the time, the details of the failures only,
                                      then ALL CHECKS PASSED or N CHECKS FAILED: names. Exit 1 on any failure.
node checks/run.mjs --changed         only what checks/check-map.json names for the files changed since HEAD
                                      (plus untracked): the Node checks, then the browser checks and the smoke sections
node checks/run.mjs --since <ref>     the same against another ref;  add --list to see the plan without running it
node checks/smoke-parallel.mjs        checks/smoke-shell.mjs in shards on separate ports (from 8201, or --port N), one merged result;
                                      [--workers N] (default: the cores, at most 4) [--only text]... [--list] [--log file]
```

**`checks/check-map.json` is the map, and the standing note of what each check covers.** Its `checks` and `browser` entries say what each check is for (`covers`); its `rules` say which checks, browser checks and smoke sections a path needs. The first rule that matches a file decides for it, a file no rule matches runs everything, and a changed check runs itself. When you add a check, add it to the map (`checks/run-check.mjs` fails until you do), and when a section or a file area moves, fix its rule. CI keeps running everything.

The smoke runner reads the section titles from `smoke-shell.mjs` and hands each worker its share through the smoke test's own `ONLY` filter, so no section is changed to be sharded. It merges the workers' output into total PASS and FAIL counts, every FAIL line with its section, and a failure for a worker that crashes, times out (30 minutes; `--timeout`) or leaves a section unrun. `ONLY=a,b node checks/smoke-shell.mjs` still runs one section by hand, and `AXE_CORE=/path/to/axe.min.js` adds axe-core to either (it is a dev tool, not a dependency). `PW_BUNDLED=1` uses Playwright's own Chromium, set unless `CHROME_PATH` names a browser.

Highlights written on a line (`src/model/marks.js`, the editor in `src/ui/onpage.js`) are painted with the CSS Custom Highlight API (`::highlight(rb-mark)` in the frame, `CSS.highlights`); a webview without it shows them once the line is left. They are kept as this resume's own line (`overrideMeta[fact].marks`), never as a change to the record's version.

Esc at the page level folds the sidebar, so every check's page sets `localStorage['rb-esc-fold'] = 'off'` (next to `rb-help-seen`) to keep it open; a check about the fold removes the key.

How the smoke test waits: `settle(page)` waits until the page is quiet, not for a fixed time. Quiet means two frames drawn, fonts loaded, no redraw waiting or running (`window.__wb.busy()`, a read-only function on the test object `window.__wb`: true while a redraw is waiting or running; nothing in the app calls it), no autosave pending or saving, the pages not moving (`body.is-moving`), no finite animation or transition running in the page or in the sheet's frame, and the pictures on an open screen drawn. It gives up after 10 s with a FAIL that names what was still going on. Elsewhere a step waits for the thing it needs (`waitForSelector`, `waitForFunction`); a fixed `waitForTimeout` is left only where the step is about elapsed time (the zoom bar's hover grace and fade, a toast measured mid-slide, the motion sections, the start screen's story, the garden). Every context comes from `newContext(options)`, which asks for reduced motion, so nothing animates and nothing has to be waited for; a section that tests the motion itself (or a behaviour that reduced motion turns off, such as the writing zoom) opts out per context with `newContext({ motion: true, ... })`. The full parallel run takes about 350 s on four workers (it took about 650 s with fixed waits); `MEASURED` in `smoke-parallel.mjs` holds the measured seconds of the longest sections, so the shards come out even. Refresh it when a section gets much longer or shorter.

## The look settings

A resume's `recipe.design` is `{ preset, fonts, size, density, colour, words }`, every key optional and absent when it is the look's default, so a resume with no `design` renders as it always did. Nothing in the files names a look except `src/themes.js`.

- **`src/model/design.js`** (pure, no DOM) holds the general tables: `PRESETS` (the section styles: `rank` one or two levels, how the main and minor labels are drawn, hairlines), `FONTS` (the three pairings and their `@font-face` files), `SIZES` (Small 12.3, Medium 12.7, Large 13.3 px), `DENSITIES` (the gap scale, the line spacing, three language columns, a smaller name), `COLOURS` (a screen shade and a print shade each), `WORDS` and `MEDIA`. `offersOf(look, format)` lists what a look offers (Small is not offered on Letter); `designOf(recipe, look)` is the settings a resume gets, the look's default where `recipe.design` asks for something it doesn't offer; `designProblems` says why for a file someone wrote (`picks.json`); `setDesign` writes no key for a default. `designCss(look, design, { medium, accent })` turns the settings into one CSS string (text size and spacing are `--type-scale` and `--space-scale` in `themes/b2-marker.css`, the font files, the section style's label rules, key words in bold, the Compact density's language columns and smaller name), and `lookCss(record, recipe, { medium })` is a resume's whole extra CSS: those settings, then the accent and an imported theme's tokens (so a tokens file still wins), then, for a pen, its rules last. The app's sheet, the thumbnails and the export (all through `extraCss` in `src/ui/design.js`) and `scripts/render.mjs` and `export-pdf.mjs` (through `scripts/lib/look.mjs`) all call `lookCss`; nothing else builds this CSS. `medium` is the export choice (`recipe.exportMedium`, *Made for* in the Export view, absent for a screen): `screen`, `print` (the highlighter shade of the colour; `onPaper` adds the `medium-print` class to the page, so a look that bleeds to the edge on a screen stops short of it) or `pen` (black and white, dotted guides). It applies to the PDF and the HTML page only: the editor, Fit and the thumbnails always measure and draw on a screen.
- **The `design` entry of a look in `src/themes.js`** says what it offers: `presets` and `fonts` (left out when every one is offered), the defaults `preset` and `font` (`preset: null` for an `earlier` look whose labels are no section style's), `sizes` where the look's own differ (Classic full width), `centred`, `ownRule` and `inkRule`. A look with none offers no settings. An `earlier` look (Tinted tabs, Mono print) renders as it did, is not in the picker, and the Design view offers one button that moves the resume to B2 Marker with the `design` that draws the same labels.
- **The renderer** reads the settings in two places (`src/render.js`). A two-level section style (`PRESETS[...].rank === 'two'`) puts the related topics (`RELATED`: certifications, patent, languages, interests) under the band above as quiet labels, unless the section's own style says otherwise (`groupedOf`, `setSectionGrouped` in `src/model/resume.js`: `''` is "not grouped"). The job title goes beside the name in Compact density only, and not in a centred header; in a centred header and beside the name its line break becomes a space, so the highlights stay on their words.
- **The measure key.** `measureKey` (`src/render.js`, which `src/fit.js` re-exports as `key`) is the paper and the theme for a resume at its look's defaults with no overlay, so measurements already stored stay valid; otherwise it adds the overlays, an imported look's id and whichever of section style, fonts, text size, density and key words differ from the look's. Colour moves no line and is not in it. A measurement is reused only for the same settings.
- **The checks.** `node checks/design-check.mjs` (Node) proves every combination a look offers gives CSS, that nothing not offered survives `designOf`, that an empty design adds nothing, and the renderer and key changes. `node checks/themes-pages-check.mjs` (Chromium) draws them: see [THEME-DESIGN-RULES.md](THEME-DESIGN-RULES.md).

### Folder linking in the desktop app

WKWebView has no `showDirectoryPicker`, so `src/store/persist.js` has a third folder object beside `fsaFolder` and `memoryFolder`: `tauriFolder(path)`, with the same methods, on the fs plugin's `readTextFile`, `writeTextFile`, `readDir`, `mkdir`, `remove` and `exists`. `tauriApi()` detects `window.__TAURI__.fs` and `.dialog`; without them (every browser) nothing changes. Link a folder then uses `dialog.open({ directory: true, recursive: true })`, and the rest of the flow (`adoptFolder`, the "use the folder's resumes?" question) is the same.

- **What is kept across restarts is the folder's path** (a string), stored where the browser keeps its handle (`handle/folder`); `folderOf(h)` turns either kind back into a folder. The permission is kept by `tauri-plugin-persisted-scope`, which saves the scope the dialog added and restores it at launch. It must be registered after `tauri-plugin-fs`, and needs Rust 1.90 or newer.
- **No prompt on reconnect.** `permission()` is `granted` while `exists(path)` works and `prompt` when it throws or says no (folder moved, deleted, scope lost). The reconnect row's button then opens the folder dialog, starting beside the old folder, so a folder that has moved can be found; a path has no permission to ask for, unlike a browser handle.
- **Questions use Tauri's own dialog (`src/ui/ask.js`).** The desktop web view does not show a blocking `confirm()`: the code carried on as if the answer were yes, and a typed draft was discarded without a word. `askOk()` uses `dialog.ask` there and `confirm()` in browsers. The folder question (`adoptFolder`) goes through it. Leaving a line asks nothing (UX-6c): what was typed is kept on this resume, so there is no "discard what you typed?" any more. `prompt()` is not available there either: in the desktop app, History has a name field on the page (`inDesktop()` in `src/ui/ask.js`), and browsers keep `prompt()`.
- **What the capability allows.** `capabilities/default.json` lists `dialog:allow-open` and the fs commands the code uses (`read-text-file`, `write-text-file`, `read-dir`, `mkdir`, `remove`, `exists`), and no fs scope. Those permissions carry no pre-configured scope, so every fs call is refused until the person picks a folder in the dialog; then the app can reach that folder and below, nothing else. Only the `main` window has them (`capabilities/default.json`); the hidden `print*` windows have `capabilities/print.json`: events and closing themselves. They call `print_pdf`, a command of the app's own, and nothing else.
- Not run on a second Mac, Windows or Linux, or in a sandboxed or notarized build. `checks/tauri-folder-check.mjs` drives the folder object against a fake `window.__TAURI__` (an in-memory disk with a scope).
- **Still disabled for lack of the File System Access API:** nothing else is gated by it. Open and Save to file in `src/data.js` use `showOpenFilePicker` / `showSaveFilePicker` when present and fall back to a file input and an anchor download. The file input is standard; whether WKWebView in Tauri saves the anchor download was not tested (the PDF has its own save path).

### The desktop title bar (macOS)

The main window has `titleBarStyle: "Overlay"` and `hiddenTitle` in `src-tauri/tauri.conf.json`, so the page runs to the top edge and the window buttons float over it. `trafficLightPosition` `{ x: 16, y: 18 }` (tao sets only x on the buttons; y is the title bar container's extra height, so the real height depends on the macOS version) puts them over the blank top margin of the page, which the layout starts at 16 px (`G` in `src/ui/layout.js`); no header or control is under them, so there is no inset and nothing to undo in native full screen. The window is dragged by `#tbdrag`, a 56 px strip along the top (nothing shows where it is, so it is generous) that `src/ui/after-boot.js` adds, stacked at z 9: above the page canvas, below the sidebar, zoom bar, fit chip and toast, so controls stay clickable and only bare canvas drags (a page panned up under it is not clickable there), with `html[data-titlebar]`, only when `window.__TAURI__` exists and the user agent is a Mac; `data-tauri-drag-region` works only on the element it is on. The main window's capability adds `core:window:allow-start-dragging` (double-click to zoom and `isFullscreen` are in `core:default`); the print windows' capability stays as it was. The page's own background (`--canvas`) is what shows behind the buttons, in both drinks and themes.

### Rules the desktop PDF export depends on

Each of these was learned from a failure on a Mac; the checks and comments name them where they can.

- **Only the modal print call.** `print_pdf` (`src-tauri/src/lib.rs`) uses `runOperationModalForWindow`. Plain `runOperation` blocks the main thread, freezes the app and wrote a PDF that grew past 600 MB. When testing a change to it, keep a guard that kills the app and deletes any test PDF over 50 MB.
- **The print window needs the app's CSP rules for styles, fonts and images.** The export is one page with inline `<style>` and `data:` fonts. `desktop/print.html` must allow them or the PDF is unstyled serif text; `checks/desktop-check.mjs` asserts it. Scripts there stay limited to the app's own files.
- **Paper follows the format.** The page size in CSS px (`pageSize()` in `src/ui/layout.js`) times 0.75 is the paper in points, so Letter prints on Letter. WebKit still takes the sheet size from the stylesheet's `@page`, which is why `.page` is one pixel shorter in print (`themes/b2-marker.css`): A4 is 1122.5 px, the page box 1123 px, and the sliver made a blank page after every page.
- **Print CSS stays plain.** macOS's PDF engine drew dark fringes round a gradient with hard `transparent` edges (the highlighter); it is one solid band now. Avoid transparent gradient stops, masks, blend modes and blurred shadows in anything the print path loads.
- **No ligatures** (`font-variant-ligatures: none` on `html, body`). The macOS engine wrote the "ff" glyph as "!" in the text layer, which breaks copy-paste and ATS parsers. Off everywhere so the screen, Fit and every export wrap the same.
- **File names are NFC.** macOS can hold names with decomposed accents, and Tauri then serves its own page instead of the file (the example resumes failed to load). The stage script normalises names, and `loadExample` skips an example that comes back as a page.

Not in the desktop build yet: the updater, a Windows PDF save (it falls back to the print dialog), a release build with signing and notarization. The Version line in Settings shows a dash, because `sw.js` is not staged.

## The one package.json

`{"type": "module"}`, three lines, no dependencies and no scripts. Node needs it to read `src/render.js` as an ES module when `scripts/render.mjs` imports it; without it, older Node treats a `.js` file as CommonJS and the import fails. It is not a build step and nothing installs from it. `playwright` stays confined to `checks/`; `scripts/export-pdf.mjs` drives an installed Chrome, Chromium, Brave or Edge over the DevTools protocol (set `CHROME_PATH` to choose one), and the app runs without any of it.

## Deploying

`.github/workflows/pages.yml` publishes to GitHub Pages on push to `main`. No build step: it copies the repo to `_site` minus `.git`, `.github`, `node_modules`, `out` and anything private, runs the guards against that assembled tree, and uploads it. The tree the browser fetches is the tree in the repo, so the same relative paths work whether you serve the folder locally or land on `https://<user>.github.io/brewcv/`.

Pages serves a project site from a subpath, so **every path here is relative**: `start_url` and `scope` in the manifest are `"."`, never `"/"`. The preflight fails on any root-absolute `href` or `src`.

The service worker (`sw.js`) is cache-first on a deployed copy and network-first on localhost. Its cache is the app's version; the deploy appends the commit (`0.8.0+1a2b3c4`), so every deploy replaces installed copies' caches and there is nothing to bump by hand.

## Real data is not in this repo

Contact details live in `identity.local.json`, **outside the repo** (see below). The frozen 0.1.0 documents carry `{{email}}`, `{{phone}}` and `{{city}}`, and `scripts/lib/identity.mjs` fills them in for the checks that measure those documents (`measure.mjs`, `render-diff.mjs`). The one-off script that extracted the first library from them, and its data, live outside the repo. Without that file everything runs on placeholders.

Nothing in `templates/` carries any of it any more: the content is a hole, the library lives outside the repo, and a rendered document goes to `out/`, which is gitignored.

`checks/preflight-deploy.mjs` enforces it. It runs against the tree about to ship and does not need the real values to catch them: in a repo whose only person is fictional, any contactable email address or real-looking phone number is a finding. It also refuses a `resume-data.json`, a `*.local.json`, a recipe, a PDF, an image outside `icons/`, a root-absolute path, and a service worker whose precache list points at a file that is not there.

```
node checks/preflight-deploy.mjs          # exit 1 means do not publish
```

### `.gitignore` covers the tree. `history-scan.mjs` covers the past.

`preflight-deploy.mjs` reads the tree about to ship. It says nothing about the commits behind it: a file added and deleted again is still in every clone, and preflight will report **clean, safe to publish** regardless.

```
node checks/history-scan.mjs              # run this BEFORE adding a remote
```

It scans every revision for contactable addresses, phone numbers, embedded images, and filenames that should never have existed, deleted or not.

**While the repo is local and unpushed, a bad history costs one command to fix:**

```
git checkout --orphan clean && git add -A && git commit -m "…"
git branch -D main && git branch -m clean main
```

After a push it costs a force-push that rewrites every clone, and the old objects stay reachable on GitHub's side for a while regardless. Commit freely now, run `history-scan` before the first `git remote add`, reset the history then if it finds anything.

### The pre-push hook: the check you do not have to remember

Hooks live in `.git/hooks`, which is not part of the repo, so each clone installs it once (worktrees share one hooks folder):

```
node scripts/install-hooks.mjs            # adds ONLY a pre-push file; your other hooks are left alone
```

`git push` then runs `scripts/pre-push.mjs`, which refuses the push when what is about to be published holds something private:

1. **The commits being pushed** (not the whole history) go through `checks/history-scan.mjs` with the range git gives the hook: private file names (a renamed identity or deny file, archives and backups, recipes, a library), contactable addresses and phone numbers, your private values in commit messages, and author identities outside `commitEmails`.
2. **A push to `main`**, which the Pages workflow deploys, also assembles the site the way `.github/workflows/pages.yml` does, from the pushed commit with `git archive` (so ignored files cannot get in; the excludes are read from `pages.yml` itself), and runs `version-check`, `name-check` and `preflight-deploy` on it. CI runs the same gates but cannot recognise your private values; this one can, because it runs on your machine. It is also how a deploy that would have been refused (the desktop icons and config in the site copy) is caught before the push, not after.

`git push --no-verify` skips it. If a different `pre-push` hook is already installed, the installer stops; `--force` keeps it as `pre-push.local` and runs it after ours. `checks/prepush-check.mjs` tests the script against throwaway repositories.

### The ignore rules are not anchored

Every rule matches at **any depth**: `resume-data.json`, not `/data/resume-data.json`. An anchored rule covers one directory, and a private file usually reaches a commit by being copied somewhere else first: a library dropped at the repo root to test something, a portrait left beside a template. Images are ignored wholesale with `!icons/*.png` carved back out.

**It passes as of 0.3.0**, which replaced the content in `templates/` with holes. Before the first `git init` there is no git to ask what is ignored, so the check reads `.gitignore` itself and says which way it answered. Two gitignored files extend the check for values that must never ship but must also not be written down in a public repo:

```
identity.local.json    { "email": "…", "phone": "…", "city": "…" }
deny.local.json        { "deny": ["a retired address", "an old figure"], "commitEmails": ["the address commits may carry"] }
```

**These two files live outside the working tree**, because a gitignored file inside it is still carried out by anything that copies the tree (`desktop-stage` once put `identity.local.json` into an app binary; a Flatpak `type: dir` source, a zip or an AI agent opened on the repo would do the same). `scripts/lib/private-files.mjs` is the one place that finds them: `$BREWCV_PRIVATE_DIR`, else `~/.config/brewcv` (`$XDG_CONFIG_HOME/brewcv`) on Linux, `~/Library/Application Support/BrewCV` on macOS, `%APPDATA%\BrewCV` on Windows. The old in-tree paths (`data/identity.local.json`, `checks/deny.local.json`) are still read, with a loud warning; move them:

```
mkdir -p "$HOME/Library/Application Support/BrewCV" && chmod 700 "$HOME/Library/Application Support/BrewCV"
mv data/identity.local.json checks/deny.local.json "$HOME/Library/Application Support/BrewCV/"
```

`preflight-deploy` and `history-scan` read them from there whatever tree they scan, so the gate on `_desktop --app` now knows the real values too. With no file (CI, a new contributor) they check shapes only and say so. `node checks/private-files-check.mjs` plants fake files in each place and runs the gate. `history-scan` reads `deny.local.json` only: put the identity values in its `deny` list to have commit messages searched for them.

`resume-data.json` itself lives outside the repo, and `.gitignore`, written before any other file here, keeps it and the rendered PDFs out. Check `.gitignore` before the first `git add`, not after.

## Versioning and releases

The app's version is in `package.json` and nowhere else by hand. It follows [Semantic Versioning](https://semver.org/), read for an app whose public interface is its files.

**Three different things are called versions here. Keep them apart:**
- the **app version**, `0.8.0`, tagged `v0.8.0`;
- the **file format**, `resume-data/4` (`SCHEMA` in `src/model/schema.js`), which changes only when saved files change shape, and always with a migration from the one before;
- a claim's **wording versions**, `v1`, `v2.1`, which are the user's content.

**Which number goes up.** While the app is 0.x:
- **minor** (0.8.0 → 0.9.0) for new features, and for anything that breaks: a new `resume-data/N`, a removed feature, a file an earlier version saved that no longer opens the same way;
- **patch** (0.8.0 → 0.8.1) for fixes, translation corrections and docs, with nothing new to learn.

From 1.0.0 on, breaking changes take the major number instead, and features the minor. Moving to 1.0.0 is a decision, not a count: when the format and the interface are ones you will keep supporting (for example, once the translations have had their native review).

**Day to day.**
- Every user-visible change gets a line under `## Unreleased` in `CHANGELOG.md`, in the same change, under *Added*, *Changed*, *Deprecated*, *Removed*, *Fixed* or *Security*, in that order. Describe the result, not the steps: if an unreleased entry is revised before the release, edit it rather than adding another. Internal refactors and check-only changes need no entry.
- The changelog is for the app's users, to skim. Each entry is one line: a bold phrase saying what changed for them, then at most one short sentence (what happens to saved resumes, say). No file names, pixel values, check names or how a bug came about: those go in the commit message.
- No milestone or stage numbers in code, check names, comments or commit messages. Name the feature, or the version when history matters (`before 0.5.1`, `the 0.4.0 pins`).
- `package.json` keeps the last released version until the next release; `sw.js` needs nothing, because the deploy stamps the commit into its cache name.

**Releasing.**
1. Decide the number from what is under `## Unreleased`.
2. In `CHANGELOG.md`, rename `## Unreleased` to `## X.Y.Z - YYYY-MM-DD` (today), and open a new, empty `## Unreleased` above it.
3. Set `"version"` in `package.json`, `VERSION = 'X.Y.Z'` in `sw.js` and `APP_VERSION` in `src/store/persist.js` (the version a saved file says wrote it; `checks/savefile-check.mjs` insists it equals package.json's), plus `version` in `src-tauri/tauri.conf.json` and `src-tauri/Cargo.toml` (building updates `Cargo.lock`) and a `<release>` in `flatpak/*.metainfo.xml`; `checks/version-check.mjs` and `checks/flatpak-check.mjs` check them.
4. `node checks/version-check.mjs` and the other checks pass.
5. **Before attaching any file to a release, run `node scripts/artifact-scan.mjs <files>` on it.** A binary built on your own machine embeds your home-folder paths (hundreds of them: the Rust compiler records source locations), so publish what CI built, not a local build; the scan refuses a local build and passes a CI one. It also looks for your private values and private-key markers, and cannot read inside a Flatpak bundle.
6. Commit as `Release X.Y.Z`, tag it `vX.Y.Z` (annotated: `git tag -a vX.Y.Z -m "X.Y.Z"`), and push the commit and the tag. Optionally, make a GitHub release from the tag with that version's changelog section as its notes, and attach the CI-built files (the zip and disk image of the macOS app, the plain `.flatpak`) plus a `SHA256SUMS.txt`.

Pushing to `main` deploys whether or not it is a release, so the live site can be ahead of the last tag. The changelog's *Unreleased* says by how much.

## The interface, in detail

The README lists the features; this is the full tour as it stood at 0.7.4, kept for reference.

- **First visit.** *Start from scratch* asks a few questions (about you; where you'll send it; your most recent job, one claim per line; education; skills; a photo where one is expected) and fills the page as you type. Or *Open or import a file*, or *Try it with an example*.
- **Click anything on the page** to work on it. A **bullet** shows its versions, the one in use first and in full.
- **A line only on this resume.** Enter at a job's last line, and "+ line" in the job's sidebar view, add an empty bullet that exists on this resume only, until the Review list (UX-6d) makes it a claim with a source. It is stored beside the job's bullets, not in them: `recipe.localLines = { jobId: [{ id, after, lang? }] }` (`id` is `~new-n`, `after` the bullet or line it follows, `null` for first), its text in `recipe.overrides[id]` and its highlights in `overrideMeta[id]`. An older app does not know the key, so it opens the file and leaves the line out (and calls the frozen text newer wording). `withLocal` in `src/recipe.js` merges the lines into a job's printed list; the model's `listedBullets`, `moveBullet`, `setBulletOn`, `printedFacts`, `resolve` and the renderer read it there. The line has no versions: its sidebar view is a note, the tick and *Remove this line*. Left empty it is removed when the selection leaves it (also on a phone, where nothing opens the page edit), and a line you wrote and emptied says so in a toast (Ctrl+Z brings it back). An empty line never prints: `withLocal` skips one whose override text is `''` unless the caller is the live page or a list (`blank`). A line whose anchor is gone follows the anchor's predecessor in the job's full list (`full`), and `dropFacts` re-points it; over a hand layout's page slots it prints only in the slot that holds its anchor, else the first (`slots`). `setOverride` records the language it was last typed in (`lang`), which is what the untranslated list compares. `loadResume` cleans `localLines` from a file (malformed entries, repeated or fact-colliding ids, a dangling `after`) with a warning, and `checks/lib/validate.mjs` reports a dangling `after`. Compare keys such lines by job and text. The JSON Resume file leaves it out and the pre-flight list says why; HTML, PDF and text print it. A language switch keeps its text as typed and lists it as untranslated.
- **Moving things on the page (UX-6c-ii).** `src/ui/hands.js` draws, over the page and in screen pixels, a **grip**, a **"+"** and a **photo slot** beside what the pointer is over (or what is selected), from the rectangles `sheet.js` reports (`handAt`, `jobLines`, `skillGroups`, `skillAt`, `headerRects`). A line owns the margin left of its text and the gap below it, so the gaps between lines belong to a line, and the grip and "+" stay reachable on the way to them; leaving the page waits `motion.js`'s `fast` before they go, unless the pointer is on them. **The drag rule:** a line moves only within its job (`moveBullet`, so a line only on this resume moves like any other), a skill group within Skills, a skill to a place in any group; a drop anywhere else is refused with the reason (a tip while dragging, a toast if let go) and nothing changes. The keyboard route is the sidebar's ↑ ↓ and chips (Alt+← → in a group, Alt+↑ ↓ to the group above or below), and ↑ ↓ on the focused grip. "+" at a job's end adds a line only on this resume (`addLocalLine`), written at once; beside a skill group it adds a group after that one.
- **Skills arranged on the page.** A skill set is one per job type or tag, with groups and skills per language and no versions (`record.skillSets[name][lang] = [{ id, items }]`, English as the fallback, listed as untranslated). A resume's arrangement is `recipe.skillArrangement = { from, lang?, groups: [{ id, items, label?, lang? }] }`; a group of the record keeps its id, one made on the page is `~sg-n` with a `label` of its own. `grid()` in `src/render.js` prints it where it reads a skills section's groups (the page's copy marks each group `data-variant="<id>-override"` and each skill `data-skill`); a recipe without it renders exactly as before. A group is written in place as its name, a line break, its skills (`writeGroup`: no skills left removes the group, undoable); the skills section's sidebar offers *Start from a set*, the groups as chips, and *Save as the set for the tag* (`saveSetForTag`, in the resume's language, or English for groups that are still the fallback). `resolve` builds `body.skills` from the arrangement, so the plain-text and JSON Resume exports and the pre-flight follow what the page prints; an arrangement with no skills prints no band. Renaming, merging or deleting a tag or renaming a job type moves its set and the arrangements' `from` (`career.js`'s `moveSet`).
- **The header written in place.** The name, headline and contact line are claims with versions, so one click writes them like a bullet (a line of the header: `{ kind: 'bullet', id, section: 'header' }`) and leaving keeps the text on this resume as an override; their Header level in the card opens About you, in the page's order (photo, name, headline, contact), which edits the record. An edited contact line keeps the look of its separators and the links whose words are still in the text (`keepLinks`, re-anchored); the pre-flight says when an edit dropped one. The photo slot toggles `recipe.photo.show` (`setPhoto`). A picture dropped on the window or inside the page's frame (`sheet.js` forwards the drop) asks what it is for, in a notice at the top of the editor card (focus moves to it, Esc cancels): this resume's photo, only your record's (`setRecordPhoto`), or cancel; the image is stored as `basics.image` always is (cropped to 35 × 45 mm).
- **Every printed text is written where it is printed (UX-6c-iii-a).** The annotated page marks every text: a claim with `data-variant`, a label with `data-label` (`h:<section>` on a heading, `t:<fact>` on a language's or reference's name). `indexModel` (`src/ui/select.js`) knows which fact is printed by which section (`owned`, `display`, `jobSection`), and `selOfFact` turns a printed text's key into its selection: a job's title and date line are `{ kind: 'bullet', id, section, owner: <job> }` (the chip and frame are the job's), the items of education, patent, certificates, languages, references, interests and custom runs are `{ kind: 'bullet', id, section }`, a heading is `{ kind: 'section', id, heading: true }` (key `~h:<id>`) and a language's name is `{ kind: 'bullet', id: '~t:<fact>' }`. A line only on this resume is `~new-n`, which is not a label key (`isLabelKey`). One click writes any of them with the writing element of 6c-i; the claims keep the override model (`setOverride` with `base` and `marks`, so UX-6d's Review list offers them as versions: `pendingEdits` lists them all, header facts too). A heading uses the per-language label (`setLabel` → `setSectionLabel`, the record's own words reset it); a language's name is `recipe.terms = { [fact]: { [lang]: text } }` (`termOf`, read by `ctx.term` in the renderer; the record's name resets it, and no key is left). Education's title and subtitle share one element: while the title is written its words are wrapped in a `data-write` span (`writable` in `onpage.js`) so only they are editable. `sheet.order` is every text in print order (the header facts, the summary, the headings, the items): the arrows select the next text, Enter writes it, and Tab and Enter inside a text go to the next. A selected item (not a section) is framed by `sheet.rectOfItem` (an item of education or patent as a whole, a language's name and level together, else the text), with a smaller stand-off than a section's frame (`PAD_ITEM = 2` against `PAD_SEC = 12` in `onpage.js`: the rows of a list are barely 2 px apart, so a larger pad cuts through the next row; the chip finds a free place on its own) so its neighbours are not covered; the chip names the field or a word of the content (`Page › Header › Name`, `› Headline`, `› Contact`, `› Photo`; `Page › Education › M.Eng`, `› Patent › Dose-counting`: the first word of the text, `Dates` for a date line, the pair's name for a language's or reference's text). Each writing element is named by its section and what it is (`Education, degree`, `Languages, name`, `Experience, heading`: `fieldName` in `edit.js`), and only a bullet or the summary is `aria-multiline`. A heading or a name is kept on one line (`setLabel`, `setTerm` collapse white space), in the language it was started in (`E.edit.lang`). The edits of an item, a heading or a name are overrides without a source: they print on the page and in the PDF but the text and JSON Resume files leave them out (a job's title and date line reach both files). `unexported` in `src/export.js` counts them for the pre-flight row and the TXT and JSON toasts, so the person is told until UX-6d's Review list turns them into versions. `recipe.terms` is cleaned when a saved resume is read (`cleanTerms`), scrubbed by `dropFacts`, and `switchLang` keeps `overrideMeta` with `overrides` per language. The education row in the sidebar opens the degree's own view, which has "Other fields of this entry" (the record's form: the grade, the dates, the courses; `score` and `courses` are not printed, and the printed date line is its own text) and "All of your record". In the Record the entry's name is the button that opens it. Not written in place: the page mark (`recipe.pageMark`, composed from the name), the continued heading on a second page (the first one is the heading), and a text with no version in the resume's language (it prints in English, outlined, and is written from the card first).
- **The lock (UX-6c-iii-b).** `recipe.locked` is a list of ids (a fact, a header fact, a heading `~h:<section>`, a language's name `~t:<fact>`, a local line `~new-n`, a skill group, a job or project, a section, and `PAGE`, `~page`, for the whole page), written only when something is locked (a resume with no lock has no key; an older app ignores it and allows the edit). `src/model/lock.js` has `isLocked(model, recipe, id)`, which walks up the ancestors (`parentOfId`: a line to its job, a job to its section, a section to the page, a heading or a name to its section or item, a header fact to the header) and answers by the nearest lock (`lockedBy`), so a lock holds everything inside it and nothing is stored per child. The model enforces it: `guard` throws one `LockedError` (key `ux6c.locked`) and the recipe is left as it was. Guarded: `setOverride`, `dropOverride`, `parkOverride`, `unparkOverride`, `pickVersion`, `setKeep`, `setBulletOn`, `moveBullet`, `stepBullet`, `setJobOn`, `moveEntry`, `stepEntry`, `setSectionOn`, `moveSection`, `stepSection`, `setItemOn`, `moveItem`, `stepItem`, `setLabel`, `setSectionLabel`, `setTerm`, `addLocalLine` into a locked job, `removeLocalLine`, `writeGroup`, `addSkillGroup`, `moveSkillGroup`, `moveSkill`, `applySet`, `setPhoto` and `RS.acceptNewer`. These take the record as their first argument (`setOverride(model, recipe, …)`), because the ancestors are in the record; `switchLang` and `acceptNewer` take it last and optional. The bulk functions skip: `planTag`/`applyTag` report `locked` and change nothing locked, `useLabelEverywhere` returns false for a locked heading, `newerOf` does not offer a locked line, `switchLang` leaves a locked line's text as typed (as it does a local line's), and `dropFacts` drops the lock of a claim that is gone. **Fit treats a locked line as a kept one that cannot be switched off**, derived from `locked` and not stored in `keep` (`lockedPins` in `src/fit.js`): its phrasing is fixed, it is never dropped, and nothing is added to a locked job. Fit does not reorder anything, so a locked line does not move. `locked` is in `NOT_PRINTED` (`src/model/resumes.js`), so locking is not a change since the last send; a duplicate and a copy keep it (they clone the recipe), a sent copy never changes. UX-6d's Review list skips locked lines: use `isLocked(model, recipe, id)`. **The lock in the interface:** the padlock and the switch are two small buttons at the right end of the depth row (`depthHtml` in `src/ui/parts.js` takes `lock` and `show`; `chipTools` in `src/ui/edit.js` works out what the selection holds with `lockIdOf`: a line, a job, a section, a heading `~h:`, a language's name `~t:`, a header field, a skill group, and the page when nothing is selected). The page chip and the sidebar's row are the same component, so both have them; on the page the padlock is quiet until the chip is hovered or focused (full contrast while locked), and the switch (`setSectionOn`, `setJobOn`, `setBulletOn`, `setItemOn`) takes no room until then, so the chip keeps its size and its place (`placeChip`). A locked block shows a small padlock (`.oblockmark`) at its frame's corner and no grip, no "+" (for a locked job) and no skill drag; the switch is `aria-disabled`. A click, Enter or Tab on locked text selects its block and says so (`startEdit` returns `lockedHint`; `hands.hint` puts the reason by the padlock for a moment and `say` puts it in the live region; a toast when the chip is not on the page, as on a phone); Tab and Enter skip locked texts. The padlock of a child under a locked ancestor is pressed and `aria-disabled` (label "Locked with X. Unlock X first."): a click only says so and selects the ancestor, `lockToggle` never lifts it. In the sidebar `lockPass` (run after each Edit render) gives every Outline row its padlock (`row-lock`), shows a lock icon on a locked row and greys the rows under a locked ancestor (`is-inherited`), turns off their ticks, ↑ ↓ and drag, and, for a locked selection, turns off its switches, versions, removal and heading and name boxes, with a note. Nothing the lock does is in a page, a PDF or a file. **Grips for jobs, sections and items** (`hands.js`: `frameTarget`, `placeFrameGrip`, `wire`): a grip stands on the dashed frame of the selected block at its top edge's left end (centred on the corner; else just above the edge; else along the edge to the first place clear of text, the chip and the zoom bar), and moves the block within its parent (`moveEntry`, `moveSection`, `moveItem` through `moveJob`, `moveSectionTo` and `moveItemTo` in `edit.js`); a drop outside the parent is refused with the reason, as for lines; ↑ ↓ on a focused grip step it. A skill group keeps its own grip; a one-item section has none. The smoke sections "the lock:" cover it, the grips at four sizes too.
  **No way round it (fix round):** hiding a block that holds locked content is refused (`lockedInside`, `guardOff` in `lock.js`; `setJobOn`, `setSectionOn`, `setItemOn`), showing one is always allowed (`guardUp`: only a locked ancestor holds) and the sibling loop of `setItemOn` skips locked rows. `toAuto` (a hand layout back to automatic pages) throws a `LockedError` with `ux6c.layoutLocked` when the recipe has any lock, so `moveSection`, `setSectionOn(on)` and Design > pages are refused; `restoreSnapshot` refuses (`ux6c.restoreLocked`) while the open resume has a lock, because a restore would drop it. Record edits take the open resume as an optional last argument and refuse when it holds the claim locked: `saveOver`, `deleteVersion`, `updateKind`, `setRecordPhoto`. `lockedBy` throws a `TypeError` when a resume has locks and the record is missing. `addLocalLine` skips a name a stale lock sits on, and `deleteEntry`, `deleteItem` and `deleteKind` take the locks of what is gone. Before a record delete or a change of the picture, `askIfLocked` and `askPhotoLocked` (`src/ui/ask.js`) name the resumes that hold a lock on it (`lockedOnDelete` runs the delete on copies and reads what vanished); with no lock there is no question. Every UI commit goes through the shell's wrapper, which turns a `LockedError` into the hint, so none surfaces as an uncaught error. In the sidebar the Record view's fields of a locked block (`SOFT` in `edit.js`) are read-only or `aria-disabled` with `aria-describedby` on the note, not `disabled`, so they keep their place in the tab order and the reason is reachable; a capture listener in `bind` stops the click and the change of the held ones. Fit says "N bullets kept by a lock" when locked lines are why a page stays over.
- **One look and one wording for show/hide (UX-6c-iv-b, stage 1).** Every show/hide is the pill switch (30 by 17): `showSw` in `src/ui/parts.js` for the inputs (the Outline's lines, items, jobs and sections, the views, Design's photo) and `pillHtml` for the buttons that draw it (the chip's and depth row's switch, the photo slot on the page). One wording: "Hide {name} from this resume" while on, "Show {name} on this resume" while off; the label says what it will do, so the chip's switch has no `aria-pressed`. The views name the block "this line" and "this job". The Outline's Photo row has the same switch (`data-photo`, `togglePhoto`). The padlock (chip, depth row, `.rowlock`) is one 24 px button, and padlock and chip switch draw at 55% at rest (full on hover, focus, locked); the chip's tools are always shown. Every job head in the Outline has its pill; archived lines are listed under a job's "+ n more" with Unarchive; the Fit chip stays until the next change; the Outline's "+ line here" (a line only on this resume) and the Record's "+ new claim" are two labels. `checks/symmetry-check.mjs` covers all of it (round trips leave the recipe byte-identical).
- **Every action has its inverse (UX-6c-iv-b, stage 2).** *Off sections* stay in their own row of the Outline, dimmed, with the same pill (`secHtml` in `src/ui/checklist.js` draws every section of `sectionList`; the "Not on this resume" chips and their keys are gone), so a section is turned on where it was turned off. *The tool beside the padlock* (`fix` in `depthHtml`, worked out by `fixTool` in `edit.js`, on the page chip and the depth row alike, so on a phone too, where the depth row is the only one): a line or header field with an edit shows the revert tool (`replay`, put back to the saved words: `only-remove`), a heading or a language's name with its own words shows it too (`setLabel` with an empty text), a line only on this resume shows the remove tool (`local-remove`) and a skill group shows "remove" (`writeGroup` with no text, as emptying it on the page does); all are `aria-disabled` with the lock and refuse again in the model (`guard`). *Skill sets:* "The record's groups" is the first choice of Start from a set while the resume has an arrangement of its own (`clearArrangement`, held like `applySet`), and "Delete this set" removes what Save wrote for the tag in the resume's language (`deleteSkillSet`; the tag's last language takes the key, the last tag takes `skillSets`); "+ group" adds an empty group at the end and writes it on the page (desktop only, like the page's "+"; a group cannot be written on a phone). *Resumes:* Delete sits beside Duplicate in the name window (`rm-delete`, the same as in Manage all). *A sent copy* is never edited, but it may be deleted from its own view (`deleteSnapshot`; a mistaken Mark as sent). *The toast's Undo:* `toast(msg, tone, undo)` in `shell.js` adds an Undo button (`toast-undo`, the same `store.undo()` as Ctrl+Z); it goes at the next change of the history (`toastAt`), so it can never undo something else, and the toast stays 7 seconds instead of 3.6. Every delete that says "Ctrl+Z brings it back" passes `undo` (a version, a claim, an entry, an item, a kind, a job type, a resume, a sent copy, a restore, a theme, the photo, a line, a group, a set, a language). *A language* leaves the record's list (`removeLang`, `removableLangs` in `src/model/lang.js`) when no resume, no sent copy of one and no version uses it; the name window's select lists it under "Remove a language" and the header menu (the phone's) has the same section, a language in use disabled with the reason. `checks/symmetry-check.mjs` has a round trip for each; `direct-check` the model.
- **The Review list (UX-6d).** Save to file (the Export button, Ctrl+S, the phone's button) opens it first when there is an edit or a heading to review (`pending()`: `edits.length + labels.length`; newer wording alone does not, the banner and the pre-flight Review button reach it); its Save to file saves what is left, Cancel and Esc save nothing and change nothing. A modal `<dialog>` (`src/ui/review.js`, full-screen under 720 px) whose rows are read from the model on every store change: the dialog keeps only what was typed (the sources) and what was done (the result line and its Undo). Group one, `reviewList(model, recipe).edits` (`reviewableEdits` without the held lines: a held line is the saved wording of a resume, group two's), has a row per edit: the marked diff against the nearest version (`wordDiff`, underlined and struck through as well as coloured), the reason (`suggestNumber`, cut-off 70%), **Approve (v2.3)** (`applyEdit` with `minor` or `major`: `addVersion` with the edit's `marks`, then `dropOverride` and `pickVersion`), **Update v2** when `tiny` (`applyEdit` with `over`: `saveOver` the nearest version, the edit's marks; `printersOf` names the other saved resumes that are offered the change as newer wording, without the ones that lock the line, and sent copies never change; a number change counts as a small edit), and a select (sub-version of another major, new version, replace, keep) that only chooses: the choice waits for its **Apply** button, with a line saying what Apply will do, and a Replace shows the same note as Update. `majorsOf` and `applyEdit` never take a draft or an archived version as a parent or a pick, and `applyEdit` moves the marks by the leading characters `addVersion` trims. A line only on this resume offers **Add to the record as a new line in <job>** (`addEntryClaim`, then the claim takes the line's place and marks). Headings and language names (`labels`) can only be kept (`keepLabel`: `recipe.keptLabels[key][lang]` holds the words kept, so a later change is offered again) or used for every resume (`useEverywhere`; `everywhereOf` says how many other resumes change, and the action is not offered while another resume locks the heading). A heading equal to the record's is never listed. When `requireSource` is on, a sub-version copies its parent's source, and a new major, a sub-version of a parent with none and a new claim need one typed (plain text, at most 300 characters; `applyEdit` refuses without it and writes nothing). Group two, `newer` (`newerOf`), is **Use the newer wording** (`acceptNewer`) or **Keep mine** (`keepOlder`, which now marks the line kept so it is not offered again as an edit), with **Use all the newer wording** for the lot in one step. One choice is one `store.commit`, so one undo step; Undo is on the row for the last choice only, and Approve all is one step with its Undo in the footer. Locked lines are never offered (the note counts them). After an export (HTML, text, JSON Resume; PDF once the print dialog returns) the toast carries a Review button when something is pending; the pre-flight rows 'edits not in the text or JSON Resume file' and 'newer wording' have one too. The dialog's Save to file (and Ctrl+S inside it; Ctrl+O and Ctrl+P are kept from the browser) closes it only after the file is saved. A duplicate keeps the lines its original holds (`copyOf` keeps `held`). Checks: `direct-check` and `review-model-check` (the model), `review-ui-check` (the behaviour), the smoke sections 'the Review list…', `review-check` (layout).
- **Versions you can reach, edits that become versions (UX-6g, stage a).** (1) A version row in the sidebar previews while a line is written: `previewVersion` (`shell.js`) picks the version on a copy with `pickVersion`, `onpage.afterDraw` does not put the draft back and `livePreview` waits while `ui.hoverFact` is set; when the pointer leaves, `edit.redraft()` draws the draft again (no history entry, the caret is `S.caret`). (2) The version number beside a written line is a button (`versionTagHtml` in `parts.js`, the list and its keys in `onpage.js`): hover, focus or click opens a `listbox` of numbers, an option previews through the same `previewVersion` and chooses through `use-version`. A line that is locked is never written, so its tag is only the disabled variant of the markup. Focus: `attach` does not take the focus back from `#editlay` (a redraw after typing used to, so a focused tag lost it), and the focus put back after a redraw does not reopen the list (`quiet`). A click opens the list with the focus in it (`openVers('click')`), so the arrow keys and Esc work; Alt+Down in the line is the keyboard route from the line to its list (Tab goes to the next line). (3) An edit is a pending row in the versions list (`pendRow` in `parts.js`, `pendOf` in `edit.js`), numbered by `suggestNumber`, with the Review list's own row drawn there (`pendingHtml` in `review.js` swaps the dialog's state for its own `P`; a click, a change and an input on `.pend` are handled by the same file); a dot on the version tag marks a line that is only on this resume. The edit pencil is gone on a desktop and stays on a phone, where it is the only way to write a text. (4) While a line is written (and after it, until the pointer moves) the frame has no hover outline (`rb-writing`, `rb-nohover` in `sheet.js`); the hover outline is the written line's shape (1px, 4px off). (5) The photo switch, shape and add/remove are `photoHtml` in `parts.js`, drawn in About you (`career.js`); Design keeps a note and a link.
- **Moving and adding, shown first (UX-6g, stage b).** (6) The grip is light (16 px, faint, no frame) and a hover or focus on it shades the block it moves (`.obshade`, in `#handlay`): a line, a skill group, or a job, section or item through `blockRect`. A job's and a section's grip is reached from its heading: `sheet.handAt` also returns `job` (the title and date line, `jobHeadRect`) and `section` (the band's `.tab`), and `hands.js` stands the frame grip (`fgrip`) at that block's top-left as it does for a selection (`frameTarget(h)` takes the hovered heading, else the selection, with the same lock and parent checks). A click still writes a line. (7) The drag preview is the page's DOM moved by a CSS transform only, never the model and never the store: `sibsOf` measures the block's siblings once when a drag starts (a transform would move the measure), `preview` lays out each page's blocks again with the dragged one taken out and put at the drop place (the gaps between blocks kept) and `sheet.nudge` moves the siblings (a `play()` slide, `fast`, none under reduced motion) and lifts the dragged one (`.rb-lift`, on paper-coloured background, following the pointer from where it was pressed). The drop line stays. The lifted block is clipped to the page it came from (`.rb-clip`, `overflow: clip`, set by `nudge`, removed by `unnudge`), so it never floats over the next page; the gap and the drop are unchanged. A row of the sidebar also starts a drag from its name button once the pointer has moved 4 px; a press and release without moving is still a click. The gap opens and closes page by page, so a block dragged to another page opens a gap there and closes the one it left. Esc (`escDrag`, on the window and the page's frame; a row's gesture also ignores the moves after it, `began`) puts it all back with `sheet.unnudge(true)`, makes no history entry and eats the click that follows; a refused or no-change release snaps back the same way; a drop calls the same `moveLine`, `moveGroup`, `moveJob`, `moveSectionTo`, `moveItemTo` as before. Skills keep only the drop line. The keyboard route (↑ ↓ on a grip, Alt+arrows) is unchanged: each press is a step the page shows at once. (8) A row of the sidebar drags by being grabbed: one delegated `pointerdown` on `#body` (`rowOf`: a line's `.clrow[data-bullet]`, an item's `.clrow[data-item]`, a job's `.clgh[data-job]`, an Outline section's `.srow`) that starts a drag after 4 px, never from its switch, label, padlock or version count, never on a locked row, never on touch. The place is found among the rows (`rowTo`), the page shows the same preview with the block standing in its new place, a drag outside the rows is refused with the same reason, and the drop is the same model call. A press-and-release without a move is still a click; the click that ends a drag is dropped. (9) A "+" (on the page, or the sidebar's "+ line here") shows `.obghost`, a dashed one-line ghost where the line will land (under the job's last line, or after the skill group), growing in (`play`, `ghost:in`; just shown under reduced motion) and gone on leave, blur or click. Limit: a run of items that wraps over several rows is laid out down the page, not along the rows (its drop line is exact). Checks: the smoke sections `ux6g b:` (grips, drag, rows, "+").
- **Moving things, one behaviour (UX-6f, stage 4).** All drags (a line, a skill group, a job, a section, an item, and a row of the sidebar) go through `hands.js`. (1) The grip and the "+" are tertiary presses (`press`, `data-tier=tertiary`), the plate's own tabs (see the next entry). The whole block is the handle: `pointer()` takes a press on a skill, or on a line, group, job heading or section heading (`sheet.handAt` now returns its distance `d`; within `HOLD`, 5 px, is the outline), and 4 screen px of movement starts the drag (`startDrag`, `drag.page`); the selected job, section or item has its plate's edge as a handle all round (`onPlate`: a press on it, or within 6 px outside it, that moves 4 px). A press on the text being written never drags. (2) A lifted block cannot leave its container: `sibsOf` keeps `box`, the first place to the last, and `preview` clamps the block's transform into it however far the pointer goes; out of the room `dragTo` clamps the pointer into it, so the slot latches to the nearest place of its own container; over another place's printed text (`textNear`, `RIM`) it is refused (`d.ok` false, the reason, and a faint drop line, `.obdrop.is-faint`, at the slot it is nearing); in the sidebar the same holds over rows of another container (`rowOf` gives `others`), and out of the panel nothing drops. (3) The drop is animated and never redrawn under the block: `endDrag` finds where the dragged block comes to rest (`layout`, `own`), makes the model move, and, if the history grew, calls `sheet.land(own, true)`: the same lifted element comes down from where it is (180 to `--m-travel` ms, by distance, ease-out, `fill: forwards`), its hard shadow (`.rb-lift`, the primary tier's, larger, `--plate-lift-sh`) closing and its outline fading, while the others stay where the preview put them; `sheet.hold` makes the draws wait until it has landed and `ui.morph = { kind: 'apply' }` lets the redraw slide any page break the move shifted; the new page has none of the transforms (`hands.drawn`, from `onDrawn`). Undo or Redo while it lands (`hands.settle`, from `onChange`) ends it at once; a new drag does too. Esc, a refused drop and a drop where it was call `sheet.land(null, false)`: the same motion back, the others sliding to their own places. `nudge` now slides from where an element is at that moment, so a gap that opens and closes never pops, and a block lifted first rises with its shadow. A row of the sidebar lands the block in place on the page and slides its rows to the new order (`flipRows`). Reduced motion: everything at once, the transforms left until the page is drawn again so nothing flashes. (4) The "+" stands at the bottom and centre of its block (the job, or the skill group's whole box), moving along the edge only where printed text is in the way, and the strip under the block down to it keeps the hover (`bridge`). Checks: the smoke sections `ux6f s4-1` to `s4-4`.
- **One selection system: the plate (UX-6f, stage 4b).** A block's own outline is the only selection mark, in four heights: hover (a hairline and a faint tint), selected (a 2 px line and a stronger tint), writing (pressed in: a hairline, the paper's colour and a soft inner shadow) and lifted (the same plate with the larger press shadow). One shape per level (line, group, job, section): its stand-off is `--plate-off-<level>` (4, 4, 6 and 12 px), its radius `--plate-r`, and the bigger the block the fainter its tint (`--plate-k-job`, `--plate-k-section`). The tokens are `--plate-*`, in the `:root` block of `workbench.css` (the colours are made of each drink's and theme's `--sel-mark`, `--sel-mark-soft` and `--prev-mark`, so they follow them) and nothing else paints a mark: `sheet.js` copies them into the frame (`PLATE_TOKENS`) and its one `PLATE` block of the frame's stylesheet draws every state, from the block's own classes: `rb-hot` (hover; `rb-cool` while it fades out, `--plate-a` a registered number the fade runs on), `rb-sel`, `rb-ring` (the parents of the selection, a faint ring behind it: the ring trail), `rb-lift`, `rb-socket`; the preview accent is the other colour role (`rb-hover`, `rb-prev`, `rb-find`, in the plate's shape), and dashed is kept for `rb-miss` and the socket. The colour roles are two: selection ink (what you act on) and the preview accent (what the app shows). `onpage.js` no longer draws frames (`.obframe`); the chip, the veil's hole and the grips stand on the plate's edge by `off(level)` (`plate.js` reads the tokens). The grip and the "+" are the plate's tabs (`.obgrip`, `.obplus`, in `hands.js`): the same ink, hairline and radius, flush with the plate's edge (the corner it stands on is square: `sheet.setTab`), no shadow, a tint of their own only as the plate's; the selected plate's tab inks in. The hovered block is one element at a time (`sheet.setHot`, from `hands.js`): a line, group, job (its heading) or section (its heading) with hands, else the deepest printed text under the pointer (`sheet.plateAt`). A lifted block leaves a dashed socket where it will land (`sheet.socket`, `.rb-socket`, same shape; placed by `hands.preview` from `layout().own`). A check lists every selection class the frame knows and asserts each takes its outline, shadow, radius and fill from the plate tokens, and draws each class on each level by what the browser computes: `checks/plate-check.mjs`.
- **Hover is intent, not a reflex (UX-6f, stage 4b).** The page reacts to where the pointer settles, not to everything it passes. `hands.js` `pointer()` measures the pointer's pace in screen px/s over the last `HOVER_WINDOW` (80 ms): above `HOVER_SPEED` (600) nothing starts (no plate, no tab, no "+") and what the pointer has left goes at once (`resolve(x, y, gated)`); a pointer that is slow takes the block under it in the next frame, with no added wait, except after a fast move, where the first plate waits until it has been slow for `HOVER_DWELL` (40 ms; a timer, `arrive`, finds the block a pointer has stopped on). The first move on the page after being off it has no pace yet, so it waits for the next one. The plate then fades in over `HOVER_IN` (80 ms) and the one it leaves fades out over `HOVER_OUT` (120 ms) in the frame's own transition (`rb-cool`), so there is one hovered block and, for a moment, one fading out. Leaving the page cancels a pending hover at once (a pointer that is only on its way to a tab enters it in the same breath). A press shows the plate at once with no speed test, a grip in focus shows its block's, and a step by the arrow keys is a selection, which the gate never touches; the sidebar's `.rb-hover` is not gated. Touch has no hover. Reduced motion: no fades, the gate stays. The constants are in `plate.js`; `__wb.hands.plate()` reads `{ hot, hots, n, a }` (the hovered block, how many are hovered, how many are drawn, the strongest `--plate-a`) and `__wb.hands.gate(false)` turns the gate off for the checks that are not about it (the smoke's `open()`). `checks/plate-check.mjs` sweeps the pointer across blocks fast and slowly.
- **One search (UX-6f).** Ctrl+F (Cmd+F on a Mac; Ctrl+F there is the text box's "forward") opens the app's search in every place and focuses its field: the Library's `#scr-q`, Career's `#rec-q` or, in the Editor, the bar `#find` over the page (`src/ui/find.js`). While one of those fields has the focus the next press is not prevented, so the browser's own find still works; `/` opens the search too, for a browser, a window (the Tauri one is untested) or a keyboard that keeps Ctrl+F. Plain F stays full screen and Ctrl+Shift+F is not touched. The key is handled in `shell.js` before the plain letters, and is in `help.js`'s list. One query (`F` in `find.js`) is shared by the Library's, Career's and the Editor's fields; the results are grouped in `find.js` (`careerHtml`: the Career entries and claims, every version with its number and language and the word marked, "in Career, not on this resume"; `resumesHtml`: the resumes, in Career), from `careerHits` (`model/checklist.js`) and `hits` and `prints` (`model/resumes.js`; the Library finds a resume by the lines it prints, and the selected one stays in the results). "Resumes that print this" on a claim, a version and an entry sets `F.claim`, which the Library shows as a chip. In the Editor the bar marks the lines of the open resume with `rb-find` in the page's frame (`sheet.setFind`, drawn with the other marks, never in the render), counts them and steps through them with Enter and Shift+Enter, which select the line as the arrow keys do. `checks/find-check.mjs` covers it.
- **Saving, versions and writing (UX-6f, stage 3).** Leaving a changed line toasts "Saved on this resume only" (`ux6f.savedHere`, built from the pending row's `ux6g.onlyHere`). The versions list folds when it does not fit the panel (`folded()` in `edit.js`, measured once in `afterRender`; the person's toggle is kept per claim). A second edit of a line stacks the first in `recipe.earlier[fact]` (`stackOverride`, `swapEarlier`, `dropEarlier` in `resume.js`; not printed; `applyEdit(..., at)` makes one a version without touching the page). `pagemotion.js` fades the old words out and then the new in on a linear ease, never over each other. The Career date fields are `src/ui/monthpick.js` (the app's own menu: the browser's month popup cannot be themed; values checked with `isIsoDate` in `schema.js`); a changed date follows into the printed date line in every language (`swapDates` in `model/career.js`, keeping the line's own words), and `ownWording`/`useRecordWording` are the toast's "Use the dates" for resumes that print their own words. The name, the dates and the contact line are guarded against a stray click by a per-session guard in `edit.js` (`guarded`, `softLock`; not `recipe.locked`); a check that is not about it calls `window.__wb.edit.setGuard(false)`. Full screen is **F11** (`shell.js` `key()`, before the typing return); a plain F is a letter, and `isTyping` in `select.js` is the one guard for the plain-letter shortcuts.
- **Export holds back a major problem (UX-6f, stage 5).** The pre-flight list (`preflight` in `src/export.js`) has three levels, ok, warn and bad; **bad** is major: a page that overflows, a photo that is switched on with none to print, a ⬜ placeholder, an unreviewed draft in use. Pressing PDF, HTML, text or JSON with one or more of them open (`blocked` in `ui/export.js`) shows one dialog (`#exblock`) that lists them all in the list's order: with one, Fix is the primary button in the foot and Dismiss exports; with several, each row has its own Fix and the foot has "Export anyway". A Fix closes the dialog, leaves Export and calls `goFix` (`shell.js`): to the page (letting go of an earlier selection), to About you with the photo switch focused, or to the line with its version in use focused. The next Export lists only what is still major. Every native control is the app's own: `dropdown.js` shows each `<select>` as a menu, `monthpick.js` draws months and days, `suggest.js` is the suggestion card, and `checks/native-check.mjs` keeps the list of what is left. Checks: the smoke sections `ux6f s5-8` and `s5-9`.
- **The press (UX-6f).** Pressable controls take the class `press` and a tier in `data-tier` (primary, one a view at most; secondary, the default; tertiary): a raised face with an edge and a flat shadow, a lift on hover, travel on press with the shadow closing. The travel is a transform, so nothing moves; the geometry is in `:root` (`--press-p-*`, `--press-s-*`, `--press-t-*`) and the edge and shadow colours (`--press-edge`, `--press-sh`) are in each drink's blocks. `src/ui/press.js` holds the look while Enter or Space is down. Under reduced motion there is no transition, and the pressed look stays.
- **Tags and focus.** Tag the version in use (type, Enter). Click a job type or tag to see which bullets have a matching version, then *Select bullets for X*: one undo step, never touching *Keep*.
- **Languages:** English, German, French, Spanish, Italian, Portuguese, Dutch, Polish, Czech and Hungarian. Switching moves an A4 resume to that language's A4 format. A text with no version in the resume's language prints in English, outlined, and is listed in the card; click it to write it, or mark it *same in every language*.
- **Design:** one page, two, or as many as needed; Letter or A4; six looks, each with its section style, fonts, text size, density, colour and key words; an accent with a live contrast check; themes (import CSS, JSON or DTCG design tokens, export DTCG); the photo, set in About you (cropped to 35 × 45 mm, with a note on where photos are expected).
- **Export:** pre-flight checks, then **PDF** (print, with the page size set), a self-contained **HTML page**, **plain text / ATS**, **JSON Resume**, and a **backup** of everything.
- **Files.** *⋯ › Open or import* (or drop a file anywhere, or paste JSON) reads a JSON Resume, a BrewCV record or backup, a saved resume, a theme or a photo. With a record already open it shows a **merge preview** (*Will add*, *Different values*, *Only in yours*) before anything changes. A record edited in another tool has those edits turned into versions.
- **History.** Every change is undoable (Ctrl+Z, 200 steps). Each commit is its own step; only `store.commit(fn, label, merge)` with a merge key (one continuous edit of one thing, such as the accent colour input) merges with the previous commit of the same label and key inside 800 ms. Ticks, switches, moves, locks and deletes never pass a key. Checkpoints are saved before every import, merge, replace and restore, and on each first save; *⋯ › History* compares one with now, restores it or downloads it, and compares any file with the open record.
- **Storage.** Your work is saved in this browser on every change. *⋯ › Link a folder* (Chrome, Edge) also mirrors the record to `resume-data.json` and each saved resume to `recipes/` on disk. *Back up* downloads everything in one file.
- **Actual size** draws the page at its printed size after a one-time bank-card calibration.
- **On a phone** the page fills the width and a bottom sheet lets you view a resume and pick versions. Editing is for larger screens.

## Prior art, and what was taken from it

The render half of this problem is solved several times over in the open. The library half (tagged variants of one fact, a recipe per application, a fitter that picks phrasing lengths to hit a page-fill target) has no working open-source implementation, which is why this repo exists.

**No code from any project below is vendored, copied or derived here.** Two things were taken: a published schema vocabulary, and one idea. Everything else is listed because it was read and deliberately not used, which is worth recording.

### Taken

| project | licence | what was taken |
|---|---|---|
| [JSON Resume](https://jsonresume.org) | MIT (schema) | **The field vocabulary.** `basics · work · education · publications · skills · certificates · languages · interests`, with JSON Resume's own key names: `name`, `label`, `position`, `startDate`, `institution`, `studyType`, `keywords`, `fluency` — and its `YYYY-MM` dates. The variant layer sits above it; `scripts/to-jsonresume.mjs` collapses a recipe down to flat JSON Resume, which makes every MIT-licensed JSON Resume theme an extra output and the ATS-plain path an export rather than a stylesheet. No JSON Resume code is used, and the local schema adds `facts`, `variants`, `sections` and `display` refs that JSON Resume does not have. |
| [Resume Matcher](https://github.com/srbhr/Resume-Matcher) | Apache-2.0 | **One idea, reimplemented from scratch: report the ad keywords that match nothing.** `checks/keyword-gap.mjs` is ~140 original lines with no network call and no LLM. Resume Matcher's own approach (having a model rewrite bullets to close the gap) is deliberately *not* taken: rewriting prose is exactly what this tool avoids, so this only ever reports, and a human decides whether a gap is a real one or a phrasing one. |

### Read, and deliberately not used

| project | licence | why not |
|---|---|---|
| [RenderCV](https://github.com/rendercv/rendercv) | MIT | YAML → Typst → PDF, and good at it. Confirms structured-data-to-typeset-document is a solved problem, which is this repo's 0.1.0 + 0.3.0. Has no notion of a variant, so it cannot do the part that matters here. |
| [YAMLResume](https://github.com/yamlresume/yamlresume) | MIT | Same conclusion as RenderCV, via LaTeX/HTML. One fact, one phrasing, one file per application. |
| [Reactive Resume](https://github.com/AmruthPillai/Reactive-Resume) | MIT | Its editor is better than an evening of vanilla JS will produce, but its architecture is the opposite of every constraint here: Next.js, Postgres, Drizzle, Docker against *no build step, opens from disk in 2029*. Read its theme CSS for reference for the 0.4.0 picker. Took nothing. |
| [OpenResume](https://github.com/xitanggg/open-resume) | **AGPL-3.0** | Its PDF→structured-data parser is the interesting part and would have been useful for importing old PDF resumes. Not vendored: AGPL-3.0 in a public repo needs a deliberate choice. The 0.2.1 extraction used an original parser over the project's own HTML instead (`scripts/lib/html.mjs`; the script itself is kept outside the repo). |
| [ResumeForge](https://github.com/ZenzerJs/ResumeForge) | private | Independently arrived at an "Evidence Bank" where every bullet traces to a verified item, the same idea as this repo's `source:` field. Useful as validation that the idea is right. Unusable: licence is listed as private. |
| [Typst](https://typst.app) | Apache-2.0 | An option for a PDF backend if headless Chrome proves fragile. RenderCV and ResumeForge both compile it in-browser via WASM. Not a reason to change the documents: the design is CSS and stays CSS. |
